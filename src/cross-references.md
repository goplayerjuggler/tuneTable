# Cross-references

A cross-reference links tune A to a specific reference (recording, track, discussion, etc.) that lives under tune B, so that A's row shows a "See entry under B" pointer instead of duplicating B's data.

There are two ways to create one. Prefer the first; use the second only when it doesn't fit.

## 1. Note-embedded links (preferred, automatic)

If a reference's `notes` text already names another tune — a track listing, a "see also", a passing mention — just link it inline:

```js
references: [
  {
    notes: "Has some similarities with [The Bucks Of Oranmore](theSessionId=2). I've seen settings of the two tunes that start identically."
  }
]
```

The scanned notes aren't limited to the manually-entered `references` array — a reference can also be derived automatically from the tune's `abc:`/`incipit:` block (its `S:`, `D:`, `N:` etc. fields get turned into a `referencesFromAbc` entry by `processTuneData`). If that abc-derived note already names another tune, a link embedded there works exactly the same way as one typed into a manual reference:

```abc
N: Also recorded as part of a set with [The Bucks Of Oranmore](theSessionId=2)
```

`calculateCrossRefs` scans every reference's `notes` — whether it came from `references` or `referencesFromAbc` — for `[label](theSessionId=N)` or `[label](ttId=N)` patterns and, for each match:

- resolves the target tune,
- adds a `_resolvedCrossRefs` entry to the **target** tune (the one named in the link) pointing back at the tune the note lives on,
- makes both tunes reachable by anchor link (see "How anchors work" below).

No entry is needed on the linked tune's file at all — the cross-reference is entirely derived from the link.

This is why Lucy Campbell's reference above is enough on its own to make The Bucks Of Oranmore's row show a pointer back to Lucy Campbell — nothing needs to be added to The Bucks Of Oranmore's data file.

## 2. Explicit `tune.crossReferences` (for a custom note on the reverse side)

Sometimes the pointer needs its own annotation that doesn't belong in the target's reference notes — e.g. a comment specific to how *this* tune's setting differs from what's played on that recording. For that, add an explicit entry:

```js
// 155 The Trip To Durrow
crossReferences: [
  {
    theSessionId: 1552, // Lucy Campbell
    index: 1,            // which of Lucy Campbell's references this points to
    notes: "From \"-02:58\" onwards. Here they play it \"AABBCC\", rather than \"AABCBC\"..."
  }
]
```

- `theSessionId` or `ttId` identifies the target tune.
- `index` is the position of the relevant reference in the target tune's **combined** reference list — see "Reference indexing" below.
- `notes` is optional custom text shown only on this tune's side, in addition to whatever the target reference already says.

Use this sparingly. If the target reference's own notes can just mention the tune inline (option 1), do that instead — it keeps the fact in one place and needs no index bookkeeping.

## Reference indexing

A tune's references are conceptually one combined list:

```js
referencesFromAbc.concat(references)
```

`referencesFromAbc` entries are generated by `processTuneData` from `S:`/`D:`/`N:` (etc.) fields in an `abc:` or `incipit:` block, *before* the manually-entered `references` array. So if a tune has one abc-derived reference and two manual ones, `index: 0` is the abc-derived one and `index: 1`/`index: 2` are the manual ones.

Both cross-reference mechanisms (explicit `index` and auto-detected note links) resolve against this same combined ordering, so an index means the same thing regardless of which mechanism produced it. When adding an explicit `crossReferences` entry by hand, count through `referencesFromAbc` first, then `references`, to get the right index — or, easier, just add the link inline in the target's note instead and skip indexing entirely.

## How anchors work

`calculateCrossRefs` sets two internal flags used only for rendering, not stored in source data:

- **`tune._isCrTarget`** — true if some other row needs to link to this tune's row. This gives the row an `id="cr-t{tune._crId}"` anchor. Set on:
  - the tune named in a note-embedded link (so the inline link can jump straight there), and
  - the tune whose reference is being pointed at by a reverse `_resolvedCrossRefs` entry (so the "See entry under X" link can jump there).
- **`tune._resolvedCrossRefs`** — the list of "See entry under X" pointers rendered on this tune's row, one per incoming cross-reference (from either mechanism). Each entry carries `tuneName`, `tuneId`, `refIndex`, `artistNames` (copied from the target reference), and optionally `notes` (only present for explicit crossReferences with custom text).

Duplicate pointers (same source tune + refIndex) are silently skipped, so having both an explicit `crossReferences` entry and a note-embedded link for the same pairing during a migration won't double-list it.

## Migrating away from `tune.crossReferences`

Existing explicit entries keep working — there's no need for a big-bang cutover. When editing a tune's data, if a `crossReferences` entry doesn't carry a custom `notes` value, it can be deleted and replaced with an inline `[tune name](theSessionId=N)` link inside the *target* reference's own `notes` text, achieving the same result with less bookkeeping. Keep the explicit form only where the reverse side genuinely needs its own annotation.
